# 错误码、诊断与有限状态机

## 统一错误身份

新建工程使用`fw_error_t`无符号32位错误码，`FW_OK=0`，其他错误使用稳定显式值。编码为`0xLLMMRRRR`：层ID、模块ID、模块内原因。层ID：AA=01、AB=02、AC=03、AD=04、AE=05、AF=06。模块ID在全工程注册，不重复；原因ID按模块登记，不随枚举排序重新编号。

已有公开错误ABI时保留其数值，建立显式映射并增加结构化诊断；不要把现有返回码强行cast成新层错误。模块码耗尽时扩展注册表，不截断高位造成碰撞。

错误名包含主体、操作和原因，例如：

```text
FW_ERR_SENSOR_ID_MISMATCH
FW_ERR_SENSOR_TRIGGER_UNKNOWN
FW_ERR_SENSOR_READ_FAILED
FW_ERR_SENSOR_SAMPLE_TIMEOUT
FW_ERR_SENSOR_CRC
FW_ERR_SENSOR_INVALID_STATE
```

全工程维护唯一注册表，生成/实现`fw_error_code_name()`及中文描述查询。未知码输出可见的UNKNOWN和原始数值，不映射为成功。新增终态原因同步添加名称和中文说明。

bool只用于谓词；驱动读取数据通过输出参数返回，错误通过独立返回值返回。不能将设备ID、数据值或FSM阶段塞入错误码类型中。

## 失败记录

模块最后错误/结果结构至少表达：

| 字段 | 含义 |
|---|---|
| code | 本模块可读的具体终态原因 |
| cause_code | 直接底层原因，未包装时可为FW_OK |
| native_status及有效标志 | 原生HAL/OS/设备状态；没有原生码就标无效 |
| state/stage | 失败前状态与操作阶段，不是已被改成FAULT后的值 |
| request_id | 所属请求；同步无请求时为0 |
| timestamp_ms | 本地单调时间，不能用墙钟或解析时刻冒充采样时刻 |
| file/function/line | 本层失败位置，由宏捕获，不能固定写死在公共失败函数内部 |
| origin_file/function/line | 已有底层诊断时保留其源头，不能只剩最后一层包装位置 |
| cleanup_code | 清理/停止的错误，独立于首个根因 |

公开查询API在故障清理后仍能读取记录。新请求或显式复位何时清除要明确；FAULT轮询不能每次覆盖首个原因。可选附反馈年龄、设备地址、重试次数或少量原始数据，不无限堆栈打印。

文件/函数字符串来自当前固件，发布时保留对应源码和符号。Flash紧张时可使用可解析的site ID加构建映射表替代字符串；不能只保留无人能解释的数字。模板使用直接文件/函数/行号。

底层已有详细记录时先复制其源头，包装错误另记本层位置；禁止把错误反复映射成GENERAL/FAIL后丢弃具体原因。驱动无业务策略时只报告事实，应用决定重试、降级、跳过或终止。

## FSM必须遵守

1. 用主状态枚举表达互斥阶段；每个阶段定义输入事件、迁移条件、一次性副作用、超时和退出清理。正交属性单独保存。
2. 每条进入FAULT/ERROR的路径调用统一`<module>_fail_at()`，通过宏传入`__FILE__/__func__/__LINE__`；只有该入口允许给状态赋FAULT。
3. 进入错误态之前先保存原因、失败前状态/阶段及底层诊断，再清理。清理失败不覆盖原原因。按资源能力释放锁、CS、临时缓冲和控制权。
4. switch default必须报告`<MODULE>_INVALID_STATE`并记录非法状态值；未知事件按协议规则拒绝/计数，不能默默跳DONE。
5. WAIT/BUSY/无新数据是非终态，若等待用尽预算，进入本阶段专用TIMEOUT原因。重试不重置动作总预算。
6. 收到非幂等动作的ACK超时，结果可能未知；读取状态对账或终止为UNKNOWN。未确认结果前禁止自动重复发同一动作。
7. CANCELLED与FAULT分开。取消的完成依据、停止结果和迟到事件处理必须明确，旧请求的结果不得推进新请求。
8. 终态查询和轮询无新副作用，不能反复写设备。FAULT恢复必须有明确入口，不允许旧目标因反馈恢复自行复活。
9. 明确状态由哪个任务维护；输入通过快照/队列/受控调用进入。多线程调用需要真实同步与取消提交点校验，volatile不能替代锁或原子。
10. 反馈到位、预计时长结束和软件取消是不同结果依据，调用者不能因统一DONE字段误以为物理到位已测量确认。

## 诊断与恢复边界

日志可输出：`code/name/text_zh/module/state/stage/request_id/cause/native/site/origin/time`。错误结果必须不靠串口也可读取；异步日志只消费不可变快照，不从日志文本驱动业务。

错误处理选择作用域：单次非法参数→拒绝请求；总线瞬时BUSY→预算内重试；外设不可用→该能力失效并报告；内存/内核不变量损坏→致命记录与受控停止。不会将所有错误停全机，也不会吞掉错误冒充成功。

ISR/fatal上下文不使用可能阻塞的日志、堆和mutex。其最小记录与后续任务态格式化分离；物理停止是否可保证取决于设备能力和通信状态，不能只修改软件状态就声称已停车。

## 必要验证

对修改范围覆盖：每个终态错误可读且有码；底层原因及位置保留；cleanup失败不覆盖首错；未知状态；超时回绕；重复请求；取消与迟到完成；FAULT后不再发输出；新请求清理边界。不要只用源码正则证明这些运行性质。
